The whole fixture is the committed `.devcontainer-lock.json`: its `integrity` is
DELIBERATELY WRONG for the digest its own `resolved` names — one hex character differs in
the final position. Nothing else about the configuration is unusual.

What the reference does with `integrity` is not a checksum comparison after the fact; it
is the LOOKUP KEY. Transcribed from the oracle bundle at 0.87.0
(`dist/spec-node/devContainersSpecCLI.js`), the manifest fetch is

```js

async function ji(A, e, t) { … let r = e.version; t && (r = t);

async function aQ(A, e, t, i, r) { … if (r && C !== r) throw new Error(`Digest did not match for ${t.resource}.`); … }
```

where `t` is `lockfile.features[<id>].integrity`. So when a lockfile is present the
reference pins resolution to the integrity digest — it requests
`…/manifests/sha256:<integrity>` instead of the tag, and re-checks the returned
`docker-content-digest` against it. A wrong `integrity` therefore cannot resolve, which is
what makes the lockfile a content pin rather than a record. It is also what the spec asks
for: `devcontainer-lockfile.md` lists as a goal "Improved security by detecting when a
feature's release artifact changes after its checksum was first recorded in the lockfile".

Adapted for this suite:

- **Feature repinned** from `ghcr.io/codspace/features/color:1.0.0` to
  `ghcr.io/devcontainers/features/git:1.3.2`. The Feature's identity is incidental to the
  claim here — the claim is that a lockfile whose `integrity` does not match its digest
  fails the build, and any pinned OCI Feature can carry it. (Contrast the four lockfile
  fixtures that stayed deferred in batch 2, whose claim IS a specific publisher's
  generated bytes.) `:1.3.2` is pinned exactly, not to the floating `:1`, so the digest
  cannot move under the fixture.
- **`resolved` and `version` are CORRECT** for `git:1.3.2` — only `integrity` is
  corrupted, and only in its last character (`…4846014d` → `…4846014a`). That isolation is
  the point: if `version` or `resolved` were wrong too, a CLI could fail for a reason that
  is not the integrity pin, and the case would prove nothing.
- **Base repinned** to `debian:bookworm-slim` from
  `mcr.microsoft.com/devcontainers/base:ubuntu`, for the reasons the sibling lockfile
  fixtures record: it extracts locally on the maintainer's overlay2-on-btrfs daemon, and
  it declares no `remoteUser`, so no case on this fixture enters the reference's uid-remap
  path or its `updateUID.Dockerfile-<version>` ENOENT race (#480, batch 1).
- **`--experimental-lockfile` dropped from the argv.** The flag graduated: lockfile
  generation is on by default in both CLIs at this version, and deacon has no such flag
  (only `--no-lockfile` / `--frozen-lockfile`, both of which would change the question).
  A plain `build` is the same operation upstream's test performs.
