# Does deacon behave like the DevContainers CLI?

Compared against **`@devcontainers/cli` 0.87.0** and the [containers.dev spec]
(https://github.com/devcontainers/spec) at commit `113500f4`.

This is the durable record of what we know about deacon's behavior relative to the
reference. It is **hand-maintained**: when a scenario in `parity/cases/` teaches us
something new, the row changes here in the same commit.

## How to read a row

| Status | Meaning |
|---|---|
| **Conformant and matching** | The spec defines it, deacon follows it, and the reference agrees. Nothing owed. |
| **deacon follows the spec where the CLI does not** | An observable difference in which deacon is the conformant side. The reference's deviation, not work we owe. |
| **Documented choice** | The spec is silent and the two tools differ deliberately. Each is allowlisted with its reasoning in `parity/ALLOWLIST.json`. |
| **deacon extension** | Capability the reference has no equivalent for. Nothing to compare against. |
| **Open nonconformance** | deacon is the wrong side and we know it. Always carries an issue link. |

A status is a claim backed by a scenario or an allowlist entry — never by argument
alone. Where a row has no scenario yet, it says so.

**Batch 7 took `src/test/cli.up.test.ts` and found three defects, all of them behind
fixtures the suite already owned.** SIX of its seven cases run over FOUR configs batch 1
vendored from `up` tests that nothing had ever RUN — `fx-upstream-runargs-env-subst`,
`fx-upstream-containerenv-escaping`, `fx-upstream-containerenv-dollar-escape` and
`fx-upstream-subfolder-config`, each read by a `read-configuration` case and never brought
up. That is the batch-6 lesson recurring, and MEASURED this time rather than noticed: at the
parent commit **16 of the vendored `fx-upstream-*` fixtures were referenced by
`read-configuration` operations and by nothing else.** This batch moves four of them; twelve
remain. Some of those twelve are legitimately parse-only — vendored from the reference's own
`read-configuration` tests, where parsing IS the claim — but at least one is not
(`fx-upstream-feature-no-version-tag`, from this very file). The rule this earns:
**vendoring a fixture from an execution test and covering it with a parse case records the
fixture, not the claim.**

The three defects, each with measured evidence in its issue:
[#608](https://github.com/get2knowio/deacon/issues/608) — `up --include-configuration`
serializes the configuration as substituted BEFORE the container existed, so every
`${containerEnv:*}` reaches the caller as a template while the reference resolves it (the
environment deacon actually builds is correct, so the defect is output-only);
[#609](https://github.com/get2knowio/deacon/issues/609) — a backslash in a Compose
`containerEnv` value arrives as a BACKSPACE, because `escape_yaml_value` emits a
double-quoted YAML scalar down BOTH branches and escapes on only one of them;
[#610](https://github.com/get2knowio/deacon/issues/610) — `up` demands
`--workspace-folder` where the reference defaults to the current directory, which is also an
internal inconsistency, since deacon's own `exec` and `build` already default to it.

**Two of the three carry a red-on-purpose case and one deliberately does not.** #609 and
#610 are recorded by `live-differential` cases in the nightly lane, which gates nothing, and
each asserts the FIXED behaviour so it turns green on the fix rather than on an assertion
edit. #608 has no scenario, on the [#594](https://github.com/get2knowio/deacon/issues/594)
precedent: a `spec-expectation` case would be red in `parity_docker`, a blocking PR lane, and
a `live-differential` cannot express it — the two CLIs' `up` result documents disagree
structurally by construction, so the comparison would report that disagreement forever and
say nothing about substitution. Its assertion lands with the fix, in the green case that
already exercises the flag.

**One observation was referred up rather than filed, tolerated or asserted.** The same
Compose fixture shows `containerEnv` values whose authored REAL newlines deacon delivers as
real newlines and the reference converts to the two-character sequence `\n`. deacon is
arguably the more faithful side, the spec says nothing about newline handling in
`containerEnv`, and `docs/PARITY.md` reserves a spec-silent deliberate divergence for the
maintainer — so it is named in the batch-7 inventory on
[#480](https://github.com/get2knowio/deacon/issues/480) and nowhere else. The green Compose
case omits that one key and says why.

**Batch 6 of the mining pass added five rows and found no defect — which is the result, not
the absence of one.** The batch ([#480](https://github.com/get2knowio/deacon/issues/480))
returned to `src/test/cli.exec.base.ts`, the file batch 4 opened and left 31-of-35 accounted
for, and took what its own inventory had set aside: the one negative `exec` claim it named as
the cheapest remaining item, and the lifecycle-marker block it had ruled "not `exec` claims"
and filed against the `up` row without mining. Six cases landed, all green, all measured at
oracle 0.87.0 before being written — `up --skip-post-attach`, `run-user-commands
--skip-post-attach`, `up --skip-non-blocking-commands` under two different `waitFor` values,
the object-form `initializeCommand` actually EXECUTING, and bare `exec` in a directory with no
config. Every one of them exercised a flag or a path that no scenario in the suite had ever
passed: `--skip-post-attach` existed only in the prose of three `notes` fields, and
`initializeCommand` had been parsed by a case since batch 1 and never once run.

**The one thing batch 6 could not express, it now can.** The batch reported that upstream's
restart-timing arms — a completed `postCreate` must not re-run when a stopped container comes
back up — needed a container stop/start primitive the operation vocabulary did not have, and
referred the question up rather than growing machinery on its own authority. The maintainer
ruled for the primitive. `Operation::stopContainerBefore` is that ruling: one flag, one
`docker stop` scoped to the side's own workspace label, no new operation kind and no change to
`CONSUMER_SUBCOMMANDS`. It carries three further cases and the suite's first assertion about
what a restart does and does not re-run. The rest of that report stands unchanged — the three
PTY arms remain unexpressible.

**The batch's own lesson is about a near-miss.** `--skip-non-blocking-commands` was almost
filed as a defect from a code read: the two CLIs' help texts describe DIFFERENT semantics —
the reference stops after the phase `waitFor` names, deacon's `--help` says it "skips
postStart & postAttach phases" — and those coincide only when `waitFor` is
`postCreateCommand`. Measured, deacon reads `waitFor` correctly on both the default and an
explicit value, and only its help string is wrong. That is a documentation gap, deliberately
not filed as a divergence, and it is why the behavior got TWO scenarios rather than one: the
default-`waitFor` case cannot distinguish "reads the field" from "hardcodes the default", so
a second fixture moves `waitFor` one phase earlier and makes the two readings disagree. It is
also the configuration in which a later "fix" aligning behaviour to deacon's own help text
would be a silent regression.

**All four of batch 5's open nonconformances are CLOSED.**
[#592](https://github.com/get2knowio/deacon/issues/592) and
[#593](https://github.com/get2knowio/deacon/issues/593) were fixed together because they turned
out to share a diagnosis as well as a surface: both are cases of a check or a build that ran
without carrying something the caller had already said. #592's BuildKit gate existed and asked
whether the host HAS BuildKit rather than whether this build will USE it, so `--buildkit never`
sailed past it; #593's second build — the Feature-layering pass, or the `devcontainer.metadata`
stamp — inherited neither the platform its base was built for nor the reason it had to. Both
red-on-purpose cases turned green on the fix rather than on an assertion edit, which is what the
campaign asks of them, and each gained a `spec-expectation` sibling pinning the half a
differential cannot express. Fixing #593 also CORRECTED ITS OWN SCOPE: the discriminator is not
the configuration shape the issue named but whether a second build runs at all, which a
Dockerfile configuration carrying `containerEnv` reaches just as readily.
[#594](https://github.com/get2knowio/deacon/issues/594) is CLOSED too — the smallest of the
four, and the one whose fix was mostly deleting a duplication: `build` already had the error
document and used it for the failures it caught before doing any work.
[#595](https://github.com/get2knowio/deacon/issues/595) is CLOSED too, and it is the one that cost a design rather than a patch. Its fix removes the chained build entirely: base and Features are now one BuildKit invocation over one Dockerfile, and the `devcontainer.metadata` label is computed from the base image BEFORE that build instead of stamped by a third one afterwards. With nothing handed between passes through a daemon-local tag, the `--builder default` pin that made the chain work — and that silently overrode whatever builder the user had selected — is gone from every site. **All four of batch 5's open nonconformances are closed.**

The fix for #595 also RETIRED the fix for #593 rather than building on it. #593 was closed by threading `--platform` into the second and third builds so their `FROM` could resolve the base it named; there is no second or third build any more, so nothing needs threading and the class of failure is unreachable rather than handled. Both of #593's scenarios stay green, and the one that pins `devcontainer.metadata` on an image-reference configuration with a foreign `--platform` is now proving a stronger claim than it was written for: the label it reads is written by the same single build that produces the image.

**Batch 5 of the mining pass reopened the open-nonconformance column with four rows, and
corrected three existing ones that were built on a false premise.** The batch
([#480](https://github.com/get2knowio/deacon/issues/480)) took `src/test/cli.build.test.ts`
at v0.87.0 — the densest file in the vein batch 4 opened, where upstream asserts CLI

**The three corrected rows are the batch's own lesson.** `--cache-to`, `--platform` and
`--output` were each recorded as `deacon extension` on the stated ground that the reference
CLI has no such `build` flag. It has all three, and `devcontainer build --help` says so in
one line — the rows were written from a reading of the spec rather than from the reference's
own help output, and each one closed off a comparison that was never run. The comparison, once
run, is what found #595. A row that says "nothing to compare against" is the one kind of row
that can never go red, so it deserves the same scepticism as an assertion that cannot fail.

**One case is red on purpose and the next nightly is expected red with it.**
`case-build-upstream-buildkit-never-platform-refused` asserts the FIXED behaviour and is
`live-differential`, so it runs in the nightly lane, which gates nothing. #593's case is red
in the same way, with a caveat recorded in its own row: it is arch-relative, and it agrees on

also deliberately — a `spec-expectation` case would be red in a gating lane and a
`live-differential` one cannot express it, since the two CLIs word every one of those

**Batch 3 of the mining pass reopened the open-nonconformance column with two rows, both
found by measuring something the previous batch had only reasoned about.** The batch
([#480](https://github.com/get2knowio/deacon/issues/480)) took three items:
`lockfile-oci-integrity`, which batch 2 had judged expressible and left unmeasured, and the

[#571](https://github.com/get2knowio/deacon/issues/571), CLOSED: **deacon never read the
lockfile's `integrity`.** A lockfile whose checksum did not match the Feature it named
installed anyway, the build succeeded, and deacon then rewrote the field to the digest it
had just fetched — a tampered lockfile was not ignored, it was silently repaired. The fix
is the reference's own shape rather than the obvious one: `integrity` is the manifest
LOOKUP KEY, so a Feature whose content no longer matches cannot be resolved at all, which
is strictly stronger than comparing a checksum after downloading. Closing it added two
rows the fix made observable — that `--no-lockfile` suppresses the READ and not only the
write, and that an unparseable lockfile now fails the build rather than being quietly
replaced.

[#572](https://github.com/get2knowio/deacon/issues/572), CLOSED: **a compose file's
top-level `name:` was not interpolated.** `name: ${CUSTOM_NAME}` was passed to Compose
verbatim, which rejects it as an illegal project name, so `up` failed outright where the
reference succeeds. This one was predicted from a code read and could easily have been
filed on that basis; it was measured first, which is what turned "the parser looks
line-wise" into a reproduction with an exit code. Its two siblings in the same group
MATCHED, and the pair of green rows is what said the defect was interpolation alone and
not deacon's project-name policy. The fix is the reference's own shape — an authored name
is resolved by reading `name` off `docker compose config`, where the reference's `Rp`
resolver has always taken it from — and it settled the design question the issue left open
by MEASURING it: `docker compose config` is a client-side call that succeeds with an
unreachable daemon, and the reference's compose `up` already fails outright when that call
fails, so "daemon-dependent" was the wrong frame and "no fallback" is the reference's own
answer.

Both were recorded as red-on-purpose cases asserting the FIXED behaviour, so each turns
green on its fix rather than on a case edit — which is how #571's turned.

[#580](https://github.com/get2knowio/deacon/issues/580), CLOSED: **`COMPOSE_PROJECT_NAME`
was read from one of the three places Compose reads it from.** This one is #572's aftermath
rather than a new area, and it is here because of how it was found: closing #572 produced
three side-observations, and re-measuring them against the MERGED result refuted two — they
described the code the work had branched from, not the code it shipped. The one that
survived was real and was filed with a measured matrix. Fixing it then found a fourth thing
the issue did not have, again by measuring rather than reading: the two missing sources sit
on either side of the one deacon had, so this was a PRECEDENCE defect as well as a
missing-source one, and the obvious fix — hand the question to `docker compose config`, as
the authored-`name:` branch does — answers correctly in the scenario the issue described and
incorrectly the moment both `.env` files exist.

**#557's second half — which key ORDER deacon EMITS — was ruled and landed with it.** The
spec prescribes the three properties and says nothing normative about their order, so this
was a spec-silent output surface of exactly the class
[#486](https://github.com/get2knowio/deacon/issues/486) and
[#490](https://github.com/get2knowio/deacon/issues/490) were: filed for a maintainer ruling
rather than asserted. Ruled MATCH on 2026-08-11 — deacon writes `version, resolved,
integrity`, the reference's order and the order every example in `devcontainer-lockfile.md`
uses. It shipped in the SAME change as the tolerant comparison on purpose: the order change
rewrites every existing deacon-written lockfile once, and a byte comparison still in place
would have failed `--frozen-lockfile` across that churn. No tolerance was authored, because
after the change there is nothing to tolerate — the files deacon writes are byte-identical
to the reference's.

## Coverage this document does *not* claim

Combinatorial coverage of the scenario space is **no longer tracked**. The previous
model counted obligations across a six-dimension scenario grid and dispositioned each
one; it measured a hole rather than closing it, and cost more to maintain than the
measurement was worth. What remains is the scenario suite itself: if a behavior matters,
it gets a scenario.

Four areas of coverage were **consciously dropped** when the parity corpora were
retired, rather than ported:

- **Cross-CLI container handoff** — running the reference's `up` then deacon's `up` over
  one workspace and asserting the second provisions its own container.
- **Rendered compose-project state** — *partially recovered.* The primary service's
  resolved volumes, environment, mount graph and project name are now compared by
  `case-state-compose-feature-mounts` and `case-state-compose-sidecar-volume`. What stays
  dropped is the rendered project *document* — the merged Compose file each CLI hands to
  `docker compose` — which the two deliver differently (deacon on stdin, the reference via
  a temp file) and which no channel observes.
- **Runtime-versus-merged cross-check** — relating one CLI's
  `read-configuration --include-merged-configuration` to the container it actually made.
- **Intra-deacon comparison** — diffing two deacon runs (single-container versus compose)
  against each other, with no reference side.

Each needed machinery no declarative channel provides, and none had produced a finding.
They are recorded here so their absence is a decision on the record rather than an
oversight nobody noticed.
